## 0. Invariants (every Batch 4 change must keep these; each has an existing or required test)
1. Clients only ever hold the **anon key + user JWT**. `SUPABASE_SERVICE_ROLE_KEY` exists only in Edge Function secrets / server-only env, never `NEXT_PUBLIC_*`/`EXPO_PUBLIC_*`, enforced by `scripts/check-secrets.sh` (extend it to scan for `service_role` in `apps/**` build output).
2. No migration may loosen an existing policy/grant/trigger. New migrations (0004+) are additive or tighten. A CI test diffs the policy set: removing/relaxing a policy requires an explicit "SECURITY-RELAX" PR label and fails by default.
3. Every new table: RLS enabled in the same migration, explicit `revoke all` + minimal grants, and tests (allowed + denied + anon + other-user) added to the suite before merge.
4. `FEATURES.*` flags flip to `true` only in the PR that adds the end-to-end test for that feature.
5. No OTP/session simulation anywhere. Without provider credentials the app shows "sign-in unavailable" (current behaviour).
6. Trusted-path rule: triggers treat `auth.uid() IS NULL` as trusted (service role/migrations). Edge Functions using the service role must re-check authorization themselves (see §7).

## 1. New package `@nexuse/supabase` (shared, no UI)
- `createWebBrowserClient()`, `createWebServerClient(cookies)` (via `@supabase/ssr`), `createMobileClient()` (via `@supabase/supabase-js` with an `expo-secure-store` storage adapter, `detectSessionInUrl:false`, `autoRefreshToken:true`).

## 2. Phone OTP authentication
- Supabase Auth phone provider + an SMS provider chosen by the owner (**open decision D1**: e.g. MSG91/Twilio; TRAI DLT entity + template registration is mandatory in India and takes days — start now). Use Supabase's SMS hook only if the provider needs custom delivery.
- Flow: `normalizeIndianPhone` (existing) → CAPTCHA token (hCaptcha/Turnstile, **D2**) → `signInWithOtp({phone, options:{captchaToken}})` → `verifyOtp({phone, token, type:'sms'})`. The result of `verifyOtp` is the only thing that creates a session; UI never infers success.
- Abuse controls: Supabase rate limits configured (OTP per hour, per IP), server-side CAPTCHA enforced in project settings, generic error messages (no account enumeration), resend cooldown in UI (cosmetic) backed by server limits (real).
- Copy: "Phone verified" never implies student status.
- Tests: with the provider's **test numbers/OTP feature** (Supabase supports fixed test OTPs for configured numbers in a non-production project) — clearly labelled non-production config in `supabase/config.toml` for local only; unit tests for validators; E2E marked NOT EXECUTABLE until credentials exist.

## 3. Sessions
- Web: `@supabase/ssr` cookie sessions (httpOnly, Secure, SameSite=Lax) refreshed in Next `middleware.ts`; server components read the user via `supabase.auth.getUser()` (verified with Auth server, never `getSession()` alone for authorization).
- Mobile: tokens in `expo-secure-store` (Android Keystore), not AsyncStorage; refresh on app foreground (`AppState`), sign-out clears store + wishlist sync cache.
- Logout everywhere, session expiry UI state, "re-authenticate for sensitive actions" hook (profile DOB can't change anyway).

## 6. Secure image upload (strengthens current policy; does not weaken it) — **AMENDED by D8: private bucket + signed URLs**
> Final target: BOTH buckets private. `listing-uploads` (owner write, no read for others). `listing-images` (private; **no client write**; SELECT policy for `anon, authenticated` limited to objects whose `listing_images` row belongs to a listing the caller can see under the existing listings RLS — i.e. active/reserved in an active community, or own, or staff-with-aal2). Clients obtain short-lived (e.g. 1 h) **signed URLs** via `createSignedUrls` using their own JWT/anon key, so visibility is enforced by the database, not by URL secrecy. Edge Function `process-listing-image` validates (magic bytes, decode, dimension/size limits), strips EXIF/GPS, re-encodes, writes to `listing-images`. Migration 0006 flips `listing-images.public` from `true` (current 0003, **known gap until then**) to `false`. Consequences: grid pages must batch-sign URLs; CDN caching is per signed URL; plan image transforms/thumbnails server-side; tests must prove anon cannot sign a URL for a draft/pending/inactive-community listing.
Current state: direct upload to public bucket with path/size/MIME enforced by Storage; no content verification, EXIF retained, unapproved images publicly fetchable by URL.
Target (migration 0004 + Edge Function):
1. Two buckets: `listing-uploads` (**private**, owner-folder write only, 5 MB, jpeg/png/webp) and `listing-images` (public-read, **no client write policy**).
2. Client uploads to `listing-uploads/<uid>/<listing>/<uuid>.<ext>` (path policy as today), then calls Edge Function `process-listing-image` with the path.
3. The function (service role, but first verifying the caller's JWT and that `listing.seller_id = caller`): downloads, verifies magic bytes + decodes image (reject non-images, bound dimensions ≤ 6000 px), **strips EXIF/GPS**, re-encodes (webp, max 1600 px), writes to `listing-images/<uid>/<listing>/<uuid>.webp`, inserts `listing_images` row via RPC, deletes the upload.
4. `listing_images` INSERT policy tightened: only the function (service role) inserts; clients lose INSERT (this is a tightening). Existing 8-image/path triggers stay.
5. Optional later: moderation scan hook; signed URLs for pending listings.
- Tests: path policy matrix (own/other/anon/minor), size/MIME bucket limits (Storage-level, needs real Supabase), function unit tests with fixture images (valid, polyglot, oversize, EXIF-GPS stripped).

## 7. Role-based access — **AMENDED by D5: MFA mandatory for staff**
> Enforcement in the DATABASE (migration 0004, a tightening): `is_moderator()` and `is_admin()` additionally require `coalesce(auth.jwt()->>'aal','') = 'aal2'`. A staff user with only a password/OTP session (aal1) has **no** staff powers. Admin UI includes TOTP enrolment; Edge Functions that use the service role re-check `aal2` from the caller's JWT. Tests: aal1 vs aal2 matrix across every staff-gated table/RPC (the local test shim must emulate `auth.jwt()` claims). Bootstrap order in `docs/DECISIONS.md`.
- Roles remain in `user_roles` (service-role-only writes). **No role claims trusted from the client.** UI gating uses `GET /rpc/my_role()` (new `security definer` function returning the caller's role) and `@nexuse/domain` `can()` for display only.
- Admin area (`apps/web/app/(admin)/…`, Batch 5): Next route handlers/server actions verify `getUser()` then call RPCs/RLS as the **user** (RLS enforces is_admin/is_moderator). The service role is not used by the admin UI at all, except Edge Functions for: grant/revoke role, guardian verification, account deletion — each re-checking `is_admin()` via the caller's JWT before acting, and each writing an audit row.
- MFA requirement for admin accounts (Supabase MFA/TOTP) **D5**.
- Tests: extend suite — role escalation attempts via every table/RPC; Edge Function authorization tests.
